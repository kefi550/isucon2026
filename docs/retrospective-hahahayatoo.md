## 次も使えそうな原則（直前に読み返す用）
1. **最初の1時間で、スコアの仕組み・守る条件・サーバー構成・計測を揃える。** 最適化はその後。
2. **構成の案を2〜3個書き出し、柱を先に決める。** 案は見積もってその場でやるか決め、保留にしない。
3. **期待値と実測の差を放置しない。** 説明しきれない差には、コードに書いていないコスト（既定値、ドライバー、カーネル、付属のサービス）が隠れている。
4. **重い処理は「消す → 減らす → 速くする」の順に考える。**
5. **リクエストは「エンドポイント × ステータス × 送信元」で割って見る。** 点にならないリクエストのコストも数える。
6. **律速は移る。** 大きな変更のたびに測り直し、一度戻した施策も見直す。
7. **判断は点だけでなく中身の数字で行う。** 設定が効いたかも、数字で確かめるまで終わりにしない。

## 次回の始め方

### 問題を把握するときの観点（次はどんな問題でも、最初にここを押さえる）
#### 1. サーバー構成と、台ごとの差
- **見ること**: 台の数と役割、CPU のコア数と**型番**（命令セットの差）、メモリ、ディスク、台どうしの通信の遅延と帯域、通信の経路の制約（規約で決まっている経路）。
- **わざと差が付けられていないかを疑う**。差があるなら、それは出題の意図（どこに何を置くかを考えさせる）である可能性が高い。
- 今回の例: 4台すべて2コアだが、アプリの1台だけ古い世代の CPU で SHA 専用命令がなく、署名の計算が他の台の約3倍遅かった。リージョン間は往復約100ms で、同じリージョンの台どうしだけ約1ms。サーバー間の通信は、ルーター経由が必須だった。

#### 2. スコアに何が効くか
- **見ること**: 配点表だけでなく、「何が増えると点が増えるのか」という仕組みそのもの。ベンチマーカーのログ（人数、日数、増え方など）と、自分たちの数字の変化を突き合わせて確かめる。
- 倍率や重みが偏っている部分（今回ならリージョンの倍率）があれば、そこを伸ばす方針を最初に決める。
- 今回の例: スコアは「各リージョンの利用者が日ごとにどれだけ増えるか」でほぼ決まり、**人数の伸びは応答時間で決まっていた**。倍率1.5倍の2リージョンが遅くて伸びなかった。これに気づいたのは午後の半ばで、遅すぎた。

#### 3. 律速はどこか（そして、それが移っていくこと）
- **見ること**: CPU・ディスク待ち・メモリ・ネットワーク（遅延と帯域）・ロック待ち・接続プールの待ちを、全台について同時に測る。「どこが空いているか」も同じくらい大事（逃がし先になる）。
- 1つ直すと律速は移る。直すたびに測り直す。
- 数字が説明しきれないとき（例: DB の CPU が上限なのに、クエリの実行時間の合計では説明しきれない／軽い API なのに想定より遅い）は、**目に見えないコスト**を疑う: 接続の暗号化（TLS）、接続の確立や生存確認の往復、計画の作成、ログの量、GC、標準ライブラリの実装の無駄。
- 今回の例: 序盤は DB との往復回数、途中から DB サーバー（2コア）の CPU とメモリ。アプリの1台は署名の計算で CPU を使い、他のアプリの2台は CPU がほぼずっと空いていた。DB の CPU を食っていたものには、DB 接続の TLS や、画像のクエリの計画の作成のような、コードからは見えないコストが含まれていた。

#### 4. 守らなければいけない条件
- **見ること**: 整合性の条件（どこまで古いデータを返してよいか）、FAIL や失格の条件、初期化の制限時間、再起動の後の確認（追試）の内容。
- 「ここまでなら緩めてよい」という許容範囲は、そのまま最適化の余地になる。
- 今回の例: 書き込みはリージョンをまたいでも即時に読めること（例外は削除した投稿の画像の5秒だけ）。初期化は1分以内。追試では、全台を再起動したあとにデータが残っているかを確かめられる。

### 最初の1時間でやることリスト
1. マニュアルとレギュレーションを読み、**スコアの決まり方**と**守るべき条件**を特定する（観点2・4）。
2. **ベンチの利用者の動きを書き出す**: どの順に何をするか、どこに期限や待ち時間があるか、どこで点が入るか。点が入るまでの経路のうち、時間で点を落とす場所が、最初に速くすべき場所になる（今回なら、通知 → 投稿 → フィードの経路）。AI にはコードの説明ではなく、「利用者の動きを、時間の制約と配点つきで」と頼む。
3. **主な応答の各項目が、どこから来ているかを表にする**（どのテーブルのどの列か、計算で出せるか）。別のデータから導ける書き込みや、作らなくてよい行が見つかる（今回なら、通知の行）。
4. **サーバー構成と台ごとの差**を、実測で確かめる: CPU の型番と命令セット、メモリ、台どうしの往復時間と帯域（観点1）。
5. 計測の仕組みを整える: アクセスログの集計（**エンドポイント × ステータス × 送信元**で割る）、アプリのプロファイラー、DB の統計、全台の CPU・ディスク・メモリ。付属のサービス（guard など）も含める。ベンチの開始を自動で検知して記録できるようにしておく。
6. 初期状態で1回ベンチを回し、**律速と、空いている資源**を特定する（観点3）。あわせて、**期待値と実測の差**を測る: 主な API の「往復の数 × 往復時間」と実際の応答時間、DB の CPU の使用量とクエリの実行時間の合計。差が大きいところに、目に見えないコストが隠れている。
7. 構成の案を2〜3個書き出して、柱を決める（どこにデータを置くか、空いている台に何を逃がすか）。細かい最適化はその後。

## 競技中の進め方

### 反省
- 計測の仕組みを整えたのが後半だった。pprof・DB の統計・アクセスログの集計は、最初の1時間で揃えるべき。
- 改善の多くが「往復を減らす」「クエリを軽くする」という今の構成の中での最適化だった。構成（データを利用者の近くに置く、空いている台に計算を逃がす）の判断が遅れた（詳しくは「見落としていたもの」の C）。
- スコアの揺れ（同じコードでも数％〜1割）を、1回の結果で判断してしまう場面があった。→ 差が揺れの幅に収まるときは、2回回すか、点ではなく中身の数字（リージョン別の人数、エラーの数、律速の資源の使用率）で判断する。
- 一度「効かなかった」と戻した施策（接続数を増やす、事前の読み込みなど）を、律速が変わったあとに試し直さなかった。18万点の記事の言葉で言えば、**撤退の判定は、律速が変わると無効になる**。戻した施策は一覧にしておき、大きな変更のあとに見直す。
- プロファイルを節目ごとに取り直していなかった。大きな変更のたびに pprof と DB の統計を取り直して、律速が移ったかを確かめる。

### 18万点の記事から取り入れたいこと
- **設定が効いているかを、起動ログやカウンターで確かめる。** 記事では、環境変数の空白で設定が読み込まれていなかった事例があった。設定を変えたら、効いたことを数字で見るまで終わりにしない。
- **1施策1コミット、環境変数で切り替えられるようにする。** 撤退を数分で済ませられる。
- **ベンチの稼働率を上げる。** 記事では目標8割に対して 40〜50% だった。ベンチを回していない時間は、改善の速さを直接落とす。
- **いつ、何点で止めるかを、終盤の前に決めておく。** 最後の投入の結果を確認できないまま終わるのを防ぐ。

### 正しさの確かめ方
- 等価性テストで「レスポンスが変わらないこと」を確かめながら進めたので、FAIL は事故以外では出なかった。高速化の前に、今の応答を固定するテストを書く。
- ただしテストは重くしすぎない（今回は一時、10万回以上のリクエストを流すテストを書いて時間を使った）。

### 見落としていたもの（上位の記事で効いていたのに、やっていない）

2本の記事に共通していて、自分たちもやっていたもの: 画像の検証をヘッダだけにする、初期画像をファイルで返す、署名の事前計算とキャッシュ。ここまでは同じ方向に進めていた。差が付いたのは以下。

#### A. 思いつきもしなかったもの

##### A-1. DB 接続の TLS
- **何だったか**: pgx は既定（`sslmode=prefer`）で TLS を使う。外したら DB の負荷が大きく下がった（負荷の平均 11.2 → 6.3）。
- **兆候はあった**: DB の CPU が張り付いているのに、pg_stat_statements の実行時間の合計では CPU の使い道を説明しきれなかった。vmstat でも `sy`（カーネル側）が高めだった。
- **なぜ思いつかなかったか**: 「DB が重い = クエリが重い」という前提で、クエリの統計しか見ていなかった。接続そのものにかかるコストは、どの統計にも出てこないので、見る対象に入っていなかった。
- **どうすれば思いつけたか**（TLS は今回の例。次は別のものが隠れている）:
  - **説明しきれない差を放置しない。** 「CPU 使用率 × 時間」と「クエリの実行時間の合計」を並べて、差が大きければ、クエリの外（接続・暗号化・プロセス管理・ログ）に原因があると考える。
  - **クエリ単位ではなく、プロセス単位で見る。** DB 側で `perf top` や `pidstat` を見れば、暗号化の関数が上位に出ていたはず。アプリの pprof と同じように、DB にもプロファイラーを当てる。
  - **ドライバーと DB の既定値を、最初に一度読む。** 暗号化、接続の確立、ステートメントのキャッシュなど。既定値は言語・ドライバー・DB ごとに違う（例: Go の MySQL ドライバーは既定で TLS を使わない）ので、毎回確かめる。
  - **ネットワークの区間ごとに点検する。** 「暗号化しているか / 圧縮しているか / 接続を使い回しているか」を、クライアント→nginx、nginx→アプリ、アプリ→DB のそれぞれで確認する。台どうしの往復が大きいなら、カーネルの `tcp_slow_start_after_idle=0`（しばらく使っていない接続で、送る量を絞り直さない）も確認する（18万点の記事で使われていた）。

##### A-2. 接続を取り出すたびの生存確認の往復
- **何だったか**: database/sql と pgx が、プールから接続を取り出すたびに生存確認をしていて、europe と america では1回 100ms 余分にかかっていた。
- **兆候はあった**: 投稿期間の取得は、クエリ2本なら europe/america で約 0.2 秒のはずが、実際は 0.6 秒前後だった。
- **なぜ思いつかなかったか**: 「遠いから遅い」で納得してしまい、何往復しているかを数えなかった。アプリのコードに書いていない往復は、コードを読んでも見つからない。
- **どうすれば思いつけたか**（台どうしの往復が大きい問題ほど効く。1リージョンで往復が 1ms 未満なら、効果は小さい）:
  - **遅さの予算を立てる。** 「この API はクエリ n 本 = 台どうしの往復時間 × n のはず」と予想を先に書き、実測と比べる。予想より遅ければ、見えない往復がある。
  - **実際の往復を数える。** 短時間だけ DB の `log_statement=all` を有効にする、または `tcpdump` で1リクエスト分のパケットを数える。コードではなく線の上を見る。
  - **ライブラリの裏の動きを一度読む。** 接続の取り出し・返却で何をしているか（`ResetSession`、生存確認、`DISCARD ALL` など）は、遠い台があるときほど効く。

##### A-3. 通知の行を作らない
- **何だったか**: 投稿期間が始まるたびに 5,000 行の通知を INSERT していたが、応答の中身はすべて投稿期間の1行から作れた。
- **兆候はあった**: DB の負荷の上位に、通知の INSERT が入っていた。
- **なぜ思いつかなかったか**: 書き込みは「速くする」対象としか見ておらず、「そもそも要るか」を問わなかった。元の実装の形（行を作って配る）を前提にしていた。
- **どうすれば思いつけたか**:
  - **書き込みごとに「後から計算で出せないか」を問う。** 応答の各項目が、どのテーブルのどの列から来ているかを一度表にする。全部が別の行から導けるなら、その書き込みは要らない。
  - **重い処理を見たら、まず「消せるか」、次に「減らせるか」、最後に「速くできるか」の順で考える。** 今回は3番目から入っていた。
- 2本の記事が両方とも行を作らない形にしていて、18万点の記事では 36,401 → 52,590点と大きく効いていた。

##### A-4. 攻撃のリクエストを DB に届く前に止める
- **何だったか**: 18万点の記事では、asia1 に来た約6.6万リクエストのうち約4.8万件が、ログインの総当たりと不正な署名の画像取得だった。ログインの 401 と、既に分かっている不正な署名の 403 を、DB に問い合わせずに返すようにして 47,864 → 58,728点。
- **自分たちは**: isureal-guard が IP を BAN する仕組みは読んでいたが、「攻撃がリクエスト全体のどれくらいを占めるか」は数えていなかった。
- **なぜ思いつかなかったか**: アクセスログをエンドポイント別の合計と応答時間で見ていて、「正常な利用者のリクエストを速くする」ことしか考えていなかった。失敗するリクエストは、点にならないので見る対象から外れていた。
- **どうすれば思いつけたか**:
  - **リクエストを「エンドポイント × ステータス × リージョン（送信元）」で割る。** 合計だけでは、失敗のリクエストが正常なものに紛れて見えない。401 や 403 が大量なら、それ自体が負荷の大きな部分になっている。攻撃がない問題でも、エラーや途中で切られたリクエスト（499）が多い箇所が見えるので、どんな問題でも最初にやる。
  - **点にならないリクエストのコストも数える。** ベンチマーカーが不正なリクエストを混ぜてくる問題では（最近は多いが、毎回ではない）、「いかに安く断るか」も最適化の対象になる。
  - **付属のサービス（guard など）も計測の対象に入れる。** 記事では guard の設定1つで約18% 効いていた。アプリ本体だけを見ない。

#### B. 検討したが、誤って却下したもの

##### HMAC の実装の高速化
- **何だったか**: 鍵ごとの途中の状態の使い回し（+55%）、複数の署名を並べて AVX2 で計算（+17%）。
- **なぜ却下したか**: 「標準ライブラリの SHA-256 はもう十分速い。HMAC は最小」と早く結論づけた。
- **どうすれば正しく判断できたか**:
  - **重い計算は、理論上の最小と実測を比べてから「もう最小」と判断する。** 今回なら、SHA-256 のブロック数 × 1ブロックの時間と、実測の1件の時間を比べればよかった。差があれば、計算以外のコストが残っている。
  - **pprof を行単位で見る。** 関数単位では「標準ライブラリの中」としか見えないが、行単位なら `Reset` や `Sum` の割り当てのような無駄が見えたはず。
  - 今回の手法（HMAC の ipad/opad の途中の状態の使い回し、複数をまとめて SIMD で計算）そのものは、今回限り。

#### C. 案は出たが、やらなかったもの

##### 署名 URL の有効期限の丸め
- 「前（早い時刻）」に丸めると通る（12時間単位まで）。後ろにずらして FAIL したので、方向ごと諦めた。
- → 1回の失敗で案ごと捨てない。条件（方向・幅）を変えて切り分けてから判断する。ただし時間は限られているので、**試し直しが安く、当たれば大きいときだけ**。

##### 構成を変える案（地元で書き込みを受ける / 読み取りのレプリカを置く）
- **上位2本の構成は正反対だった**:
  - 20万点: europe と america の投稿と写真を、地元の台で受ける（書き込みを近くに置く、+43.7%）。
  - 18万点: 書き込みはすべて asia1 に転送し、europe と america は同期レプリカ（`remote_apply`）から読む（読み取りを近くに置く）。コミットごとの同期待ちは、約5ms ごとにまとめて待つ形にした。非同期レプリカは実測で FAIL していた。
- **自分たちは**: どちらの案も出ていたが、構成を大きく変える判断が遅く、「DB は1台、アプリは各リージョン」という初期の形のまま終わった。
- **なぜやらなかったか**: 今の構成の中での改善が毎回少しずつ点になっていたので、大きな変更に踏み切るきっかけがなかった。整合性の条件で落ちるかどうか、どれくらい伸びるかの見積もりもないまま、案が宙に浮いていた。
- **次はどうするか**:
  - 構成の柱は、細かい最適化より先に決める（「次回の始め方」の「最初の1時間でやることリスト」の7）。
  - 案が出た時点で、「どの整合性の条件で落ちうるか」「応答時間がどれだけ縮むか（減る往復の数 × 台どうしの往復時間）」をざっと見積もり、やるかやらないかをその場で決める。保留のままにしない。
  - 大きな変更は、環境変数で切り替えられる形で1台から試す。失敗しても数分で戻せるなら、踏み切るコストは下がる。

## AI エージェントの使い方について
- AI に「壊さない」「わからないことは人に返す」と強く指示すると、慎重になりすぎて大きな手を打てなくなる（記事の筆者も同じ反省）。→ AI に任せる範囲（どこまでなら人に聞かずに変えてよいか、何が起きたら止めるか）を、最初に決めて渡す。
- 安全確認の重さ（等価性テストなど）と速さの釣り合いを、最初に決めておく。
